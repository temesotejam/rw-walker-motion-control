# 左支持へ移る直前に、次の一歩に残す速度から補助幅を選ぶ

11月20日の10走と22日の3走を使い、`left_transfer_carry_v1` が過去のどの指令を変えるかを調べた。比較元は15時39分の実機で使った `left_return_prediction_v1`。新しい計算が加わったのは、右ピークから左へ戻る途中で既に左補助が選ばれ、左足裏がまだ高いものの、通電と電流立ち上がりの間に左右の高さが入れ替わると予測できた場合である。

## 直近3走の停止した半周期

| 試行 | 判断時刻 | 実際の指令 | 直前の予測版を再生 | 今回の試験版を再生 |
|---|---:|---:|---:|---:|
| 14時40分　70067320 | 4.760秒 | 左28 ms | 左33 ms | 左33 ms |
| 14時42分　195727101 | 3.977秒 | 左補助なし | 左21 ms | 左21 ms |
| 15時39分　135284989 | 4.869秒 | 左15 ms | 左15 ms | **左34 ms** |

いずれもその時点までの身体・足・電流・予算を実ログの状態に固定している。14時42分の試行は3.977秒から先の機体の姿勢も、以前の半周期で新しい入力を入れた場合の姿勢も観測できていない。

15時39分は、既存版の補助判断で左向き18.35°/s、胴体は右+3.97°。現在の足姿勢・撮影遅れを補正した足姿勢、および胴体の前後傾斜速度を入れた姿勢で足裏高さが逆転するまでの時間を計算し、遅い方で**38.78 ms先**だった。推定した左円弧端は−1.909°。そこまで進んで速度を残すための要求仕事は35.72 µJ、同じ走行の成功時の中心通過速度31.39°/sを使った要求は80.79 µJ。大きい方から逆算すると40 ms、車輪の状態を反映すると34 msになる。80 msの半周期予算のうち46 msが残り、それに次の主入力の予約20 msを含む。新幅での推定仕事は60.93 µJで、要求に対してなお19.86 µJ不足する。実測した旧幅での推定仕事は13.15 µJ。仕事は低速域の外挿を含む。

予測した高さ逆転時刻は4.908秒。旧指令を使った実走の姿勢をCADに入れると、4.877秒には左足裏がまだ高く、4.904秒には低くなっていた。したがって大まかな移行区間は捉えたが、実走の幾何学的な逆転より遅い予測だった。実際の接地・荷重移行の時刻は測っていない。

同じ試行の3.127秒に実行した左補助は新旧とも26 ms。実際には左向き31.39°/sで中心を通り、次の左ピークに達した。[当時の動画と実測波形](prediction_trial_135284989.md)

## どの区間を変えたか

- 13走の全150右ピークのうち、中心までに通電を挟まず左に通過した区間は117、通電を挟んで通過した区間は21。通過前に折り返した区間はそれぞれ3と9。
- 実際に実行した左補助は29件。足角差が大きい既存の補助26件で、受信済みの画像を使って実機と同じ足追跡・姿勢選択を再生できた。11件は25 ms周期の左右足ペア、15件は周期の直後に届いた新しい左右足ペア。残り3件は足角差が小さい経路からの補助だった。
- 新しい計算が幅を変えたのは15時39分の最後の1件。実際の左補助に続いて中心を通過した20件に、新たな幅延長はなかった。ほかの8件の補助後の折返しには今回の追加機能は作用しない。過去の全停止への対策ができたとの評価はできない。
- 予測版から引き継いだ前倒し開始判定も同じ150区間で再生した。惰行で渡れた117区間の保存標本上で新規開始は0件。そのうち17区間には途中の周期標本に欠けがある。14時42分の最後のように、周期データから開始を判断した場合の電流・車輪・予算は別の実装再生で照合した。

## 入力を変えた後、機体がどう動くか

11月20日の先行8走で固定した運動モデルで、15時39分の4.869秒に15 msと34 msを比較した。どちらも実測の指令遅れ2 msを入れた。モデルは保存された約5 ms間隔の時系列を使い、開始状態は右+4.07°、左向き20.84°/s。指令イベントに記録された瞬間の値とは少し異なる。

| 予測項目 | 実際の15 msをモデルへ入力 | 新しい34 msをモデルへ入力 | 15 ms実走の観測 |
|---|---:|---:|---:|
| 右+2.16°に達したときの左向き速度 | 22.94°/s | 27.73°/s | 19.35°/s（IMU取得時刻で補間） |
| 150 ms後の左右角 | 右+0.80° | 右+0.44° | 右+1.21°（記録周期から補間） |

34 msで途中の左向き速度が増える予測だが、150 msの有効範囲では中心通過まで予測できなかった。状態が近い先行補助は1件、その状態・指令遅れ・幅すべてが近い34 msの例は0件だった。実機で検証すべき点は、左補助が実際に延長された後、機械的中心と左円弧端をどの速度で越え、動画で次の右足、左足が順に前に出たかである。

## 再現

リポジトリのルートから次を実行する。`$ref` を11月20日の10走を展開した親フォルダ、`$recent` を11月22日の3走を展開した親フォルダとする。各試行は `tools/convert_rwlog_to_csv.py` の出力をID名のサブフォルダに保存する。結果は試行ごと・半周期ごとの条件付き比較。最初に指令を変更した後の運動を元ログと同じとは仮定しない。

```powershell
$ref = Join-Path $env:TEMP 'walker_arrival1_verification_20261122'
$recent = Join-Path $env:TEMP 'walker_trial_20261122'
python -B analysis/2026-11-22-return-trial/transfer_carry_replay.py $ref $recent --json-out "$recent/transfer_carry_results.json"
python -B analysis/2026-11-22-return-trial/compare_timing.py $ref $recent
python -B analysis/2026-11-20-turn2-trial/replay_small_arc.py "$recent/195727101" --predict
python -B analysis/2026-11-22-return-trial/timing_grid.py $ref $recent --carry-trial
```

次回の実ログは `simulate.py --evaluate-run` の `observed_return_prediction` で、予測成立、要求仕事、指令幅、実行、実際に旧幅より長く通電したか、中心と円弧端に到達したかを分けて読める。古い試験のログには、新しい予測の実行結果は入っていない。

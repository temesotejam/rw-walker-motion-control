# 左足への荷重移行を補助する入力幅の再生

2026-11-20 の4走行で、実際に成立した失速救済11件を再生した。受け足が低い状態が続くと予測され、次の主入力に使う通電時間を確保できたときに限って、既存の救済入力を延長する。11件中7件で選択幅が増えた。元の走行で同じ半周期にZEROへ届かなかった4件では、救済入力がそれぞれ 12→18、27→29、28→30、20→20 ms になった。

## 入力幅とZERO通過後の余裕

予約は同じ方向で救済後に完了した主入力の最長実通電時間。その実績がまだない場合は同方向の主入力全体の最長値を使い、主入力自体が初めてなら80 msを残す。既存の救済幅がすでに予約に食い込んだ4件では追加を見送った。元の走行でZEROを越えた7件では、全件で実測された後続主入力33〜53 msが新選択後の残りに収まった。

足裏の高さ、足角とその変化率の推定には同一画像の左右の足を使った。直近の定周期パケットにその画像が含まれていた例は5件。残る6件では定周期の発行後に制御側へ届いた、より新しい両足同時検出画像とその時点までの角度履歴を参照できた。

69728952 の16.550秒では、直近の定周期パケットは判断時に25.657 ms経過していた。カメラはその後に両足を同時に検出しており、次の定周期発行を待つ間に画像3828が制御側に届いていた。撮影から34.266 ms、制御側の初回受領から8.887 msで、両足の速度推定も成立していた。この直接参照があると30 msを選ぶ。定周期パケットだけを使う場合は28 msだった。205922296 の9.398秒では足の形から27 msが候補になるが、直前までの主入力から予約は72 msであり、元の20 msを維持する。どちらの試行でも、停止を解消できるかは実際の運動で確認する必要がある。

## 再現条件

`tools/convert_rwlog_to_csv.py` で展開した試行フォルダーを渡す。Python 3.9以降とC++17対応の `g++` を使う。CSVには元幅・候補幅の電流モデル逆算値とホイール制限後の両方、選択時の足速度・追加要求エネルギー・画像取得経路を出力できる。

```powershell
$folders = 69501075,224021399,69728952,205922296 | ForEach-Object { Join-Path $env:TEMP "control_trial_$_" }
python analysis/2026-11-20-carry1-trials/replay_aid.py @folders --out "$env:TEMP/rescue.csv"
```

カメラの各画像を制御側初回受領時刻の順に供給し、定周期足推定器を各パケットの実発行時刻に呼ぶ。記録された公開回数、判断時の両足の元画像連番、0.001°単位の推定値を照合する。各救済で使われた生画像は撮影時刻・記録上の画像の経過時間・制御側到着の3条件で一意に照合した。時計はその走行の測定開始を原点とする。判断時刻には旧版が記録した入力直前のマイクロ秒時計を使った。新版そのものの実行時刻は次の測定で記録を確認する。

過去のピーク・主入力・通電完了の順にホイール保護と予約状態を更新し、同一の事前状態から元と候補の両方にホイール保護を適用する。11件すべてで元の逆算幅と制限後の通電指令幅がログに一致した。各救済時点までは元走行の記録に条件付けている。救済を延長した後の速度変化、接触力、次の救済の発生時刻、実際の主入力幅は、この再生からは決まらない。

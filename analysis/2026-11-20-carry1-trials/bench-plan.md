# 受け側予測の計算時間と判定の照合

4本の実歩行RWLOGから保存済みの計2,001枠を旧版と改修版に同じ順序で与えた。判定理由、接近・受け側・到達の区分、終端角を決めた観測の種別、方向、開始遅れ、通電幅、仕事モデル校正域の判定は、全枠で一致した。切替と終端の角度・所要時間、惰性時のエネルギー余裕、候補入力後の余裕、入力仕事の7項目も、有限値の差はすべて0で、欠測となった枠も一致した。比較は丸めてRWLOGへ保存された入力に対するPCでの再計算である。

| RWLOGの起動時刻ID | 全枠 / 受け側枠 | 全履歴1回の時間、carry1 → 改修版（ms） | 受け側1枠の計算時間、carry1 → 改修版（µs） |
|---|---:|---:|---:|
| 69501075 | 572 / 211 | 2.856 → 1.536 | 9.638 → 3.597 |
| 224021399 | 436 / 158 | 2.009 → 1.043 | 8.920 → 3.211 |
| 69728952 | 625 / 226 | 2.813 → 1.332 | 9.165 → 2.990 |
| 205922296 | 368 / 125 | 1.456 → 0.711 | 7.974 → 2.408 |

このPCでは、今回の2本の全履歴計算が約53%・51%短くなった。受け側の計算単独では約67%・70%短い。ESP32-S3上のRTOSスケジューリング、カメラ・Wi-Fiとの競合、次の観測を待つ時間、キュー上書き、記録への書き出しはこの数値に含まれない。実機で判断が使えるまでの時間は次のRWLOGの `ready_after_us` で検証する。監査の連続枠判定と実際のモータ指令は別経路で、この計算時間比較の対象外である。

## 再現

同じPCの MinGW g++ 14.2.0、`-O2 -std=c++17` を使用した。旧版はGitコミット `ab93f4d` の `src/support_transfer_plan.h`、改修版は作業ツリーの同ファイル。入力はファイル長・CRCを検証したrev1/2の監査表で、保存前にキューで上書きされた観測は補っていない。改修前後の予測値にはC++ floatの往復に十分な9桁を使用した。

全履歴の各反復は空の状態から開始し、ゲートで保留した枠も含めて半周期を順番に観測する。受け側単独の測定では、先に同じ順序で得た半周期履歴を各枠の時点で保存し、その履歴を使って予測器だけを計時した。データ入出力とメモリー確保は計時外。ウォームアップ後、各回32反復の平均を求め、新旧の実行順を交互にした全9回の中央値を表に載せた。数値はこの計測時のホスト負荷にも依存する。

```powershell
$inputLogs = @(
    "$env:USERPROFILE/Downloads/energy_control_autonomous_run_1_69501075.rwlog",
    "$env:USERPROFILE/Downloads/energy_control_autonomous_run_2_224021399.rwlog",
    "$env:USERPROFILE/Downloads/energy_control_autonomous_run_1_69728952.rwlog",
    "$env:USERPROFILE/Downloads/energy_control_autonomous_run_2_205922296.rwlog"
)
python -B analysis/2026-11-20-carry1-trials/bench_plan.py @inputLogs
```

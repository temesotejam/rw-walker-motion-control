# 足角度のセンサー読出し・認識並行処理（v25/v26）

2026-11-17更新。目標は、カメラドライバのフレーム時刻から制御側の初回受取りまでを約20 msへ近づけること。これは露光開始からの光学的遅延を測った値ではない。USB接続中はモータを動かしていない。

## 比較の基準

同じPC・機体の停止中にHTTPで抽出した標本では、v23は中央値47.7605 ms、v24は45.849 msだった。v24は上側マーカーの画像処理を受信と並行させたが、センサーから全画像が届くまでの中央値36.080 msが残った。v24の180秒試験は167標本、初回受取り時刻のある標本は161件。詳細は `FOOT_OVERLAP_V24.md`。

## 変更

- GC0308のCIS行間引き `P0:15=4a` と出力間引き `P1:54=12` を併用。旧320×240と区別し、生画像は320×236・75520 bytesとして検証する。
- 全幅320画素と従来の探索範囲を維持。静止画像の比較から、従来の論理行 y を生画像の y−2 に対応させる。必要な66行がすべて実在することをコンパイル時・ホスト試験で検査する。全角度での動的な対応精度は未検証。
- 水平ブランキングは96。受信DMAの区切りは1280 bytes。最終バッファは75520 bytesが揃った場合だけ公開し、不完全な画像を完成画像として扱わない。
- 取得開始時に既に完了して待っている画像を最大1枚破棄し、新しい画像を待つ。33.333 msの取得ワーカー周期と1280件の記録容量は維持する。
- 停止中の確認画像は最大5 Hzで作成し、画像の公開コピーを足角度の公開後に行う。省略した確認画像とその時刻・検出結果の組は維持する。歩行中の確認画像保持は従来どおり。
- センサー上下・左右反転のビットを一括設定し、読戻しを確認する。SDKへの要求は上下反転ありだったが、実機で読んだ値は `0x10`。要求どおりの `0x12` にすると、従来画像に対して上下と足の対応が反転した。そこで既存校正・実画像と一致する **`0x10`** を明示設定し、最終読戻しでも一致を要求する。連続したread-modify-writeと遅れた読値の組合せが原因候補であり、原因を断定してはいない。
- P1:53は実機初期値 `0x83` と資料既定値 `0x82` のみを受理し、元の値を保持する。下位5 bitは行末延長の画素数で2以上という定義に対応する。[GC0308データシート28ページ](https://download.kamami.pl/p1197045-GC0308.pdf)

## v26の追加

下側の認識を論理行174・190・206・222までの累積画像に分け、同じ順番の17個の探索テンプレートを段階的に評価する。途中の画像は所有権を持つ別領域へコピーし、時刻・画像の一致を確認するまで追跡履歴を変更しない。準備が済んだ両側の結果を使う場合は、完成画像からの66行・21120 bytesの再コピーも省略する。

最後の段階だけ間に合わなかった場合は、完全画像をコピーした後、その同じフレームで既に計算した部分を使って残りを計算する。時刻不一致・不完全画像・無効な準備結果では従来処理へ戻る。下側の途中計算時間は状態表示用に記録し、FootFrameの保存形式は変更しない。処理を受信中へ移した分を、計算量自体がゼロになったとは扱わない。

実機の最初のv26では、画像受信・足認識ともCore0で動かしていたため、受信側の処理などで認識が中断される時間が残った。確認画像の毎画素関数呼出し19200回を行単位の処理へ置換し、上側・下側の必要行の検索をコンパイル時の固定表へ置換した。処理中で上側のコピーを一度見送ったフレームは、後続DMA区切りで再試行する。

11月17日に足認識をCore1・優先度3へ移したv26を書き込み、停止中に比較した。カメラ受信はCore0・優先度3、IMUはCore1・優先度6、制御はCore1・優先度4を維持した。Core1化による追加の遅延短縮は確認できず、歩行試験用の足認識はCore0・優先度1へ戻す。USB停止試験の制御deadlineカウンタは動作中の負荷を測れないため、ゼロ件だけを根拠に歩行中の締切維持を断定しない。

## センサー単体試験

モータ・歩行制御・Webを含まない専用バイナリで、GPIOのHREF/VSYNC、DMAイベント、画像CRCと実画素を照合した。センサー単体の値を制御側受取り時間と混同しない。

| 設定 | 観測結果 | 採否 |
|---|---|---|
| 旧QVGA、HB128 | フレーム周期約35.962 ms | 比較用 |
| native skip、HB128 | 周期約21.766 ms | 形状検証用 |
| native skip、HB96 | 周期約20.366 ms、最終DMA到着約20.169 ms。再起動後120秒で画像白化なし、左右の白マーカーあり | v25/v26で採用 |
| native skip、HB80 | 約19.666 ms。短時間のみ | 長時間未検証、採用せず |
| native skip、HB64 | 約18.966 ms。ただし90秒試験で画像が白化、最小244・最大251に潰れた | 不採用 |

横幅を狭く切る案は、従来の角度範囲とマーカー幅を失うため採用していない。生画像を240行へ無理に延長する設定も採用していない。

## 実機統合

初回は反転レジスタの読戻し不一致で停止し、次の版はP1:53の初期値相違で停止した。これらを修正したv25試作版では約25 msが観測されたが、画像が従来に対して上下反転していたため、左右対応の正しい完成版として採用していない。従来画像と一致する0x10へ修正したv26を次の停止試験で比較した。

|---|---|---|---|
| v24 | 180秒・167標本、受取161 | 45.849 / 51.642 ms | 比較基準 |
| v26初期・Core0 | 120秒・110標本、受取109 | 29.173 / 36.043 ms | 両足110/110、HTTP失敗0。末尾に確認画像取得を併用した標本あり |

Core0最適化版の持続取得は28.210 Hz。更新周期33.333 msを保持しているので、読出し約20 msを50 Hzの足角度更新と同一視しない。不完全な画像のHAL内部破棄は残っており、認識失敗カウンタとは別に扱う。

Core1試験では同一起動ID `407065312` の間に5093画像を取得し、持続取得は28.444 Hzだった。全155標本で画像時刻・両足検出・MEKFと制御状態の鮮度を確認した。開始条件の表示は154件が `ready`、1件が `frame_stale`。初回受取り時刻のある標本は146/155（94.19%）で、Core0の53/54（98.15%）より少ない。残りはHTTP抽出時点で受取り時刻が不明な標本であり、画像を失った件数とはみなさない。

Core1の中央値はCore0より1.154 ms遅く、p95はほぼ同じだった。最大値はCore0の36.422 msに対してCore1で40.304 msだが、観測時間・標本数が異なるため最大値だけで優劣を決めない。Core1の最初の約59秒に限定しても中央値28.815 msで、追加短縮は確認できなかった。受信中に計算を終えた標本は増えた一方、画像受渡しの中央値は22.515→25.260 msとなった。認識時間や並行処理の利用率だけで改善とは判定しない。

このCore1比較試験に書き込んだファームウェアは1946432 bytes、SHA256 `dd4e21830cbe786bc882db16c2e38b3101af720da15fa1f57ceb8e95b1e785a4`。この版のメタデータ全容量試験は1001422 bytesで、1 MiBまで47154 bytesの余裕があり、1280足フレーム・192エネルギー記録・96支持記録を維持した。専用ページのURLは `http://127.0.0.1:8767/foot-native-stream/`。

歩行試験用にはCore0・優先度1へ戻した再ビルド版を書き込んだ。1946432 bytes、SHA256 `7fc287d9d290ca8767cecb4d54a24306ca285c64d1f9a6abdbb054668fb90ed6`。ビルド57.249秒、実observerの7構成と9インストーラ構成の検証が成功し、app領域のみ書込み・ハッシュ照合を確認した。ドライバの書込み後リセットだけでは通常起動を確認できず、115200 baudの標準USB-JTAG reset・RTC値0確認・hard resetで復旧した。ソフトウェアのENTER DOWNLOADは使っていない。

最終Core0版は同一起動ID `2526545834` で1651画像/59.743081秒（27.635 Hz）、55標本すべて左右・ゼロ点・開始条件・MEKF/制御の鮮度が有効だった。初回受取り52件の最大値45.487 ms、画像受渡し中央値24.030 ms。v24から中央値約38.7%短縮したが20 msには未達。27.812 msは11月16日のCore0版、28.0975 msは今回の再ビルド版の値として区別する。カメラの配置はCore0へ戻し、v19の歩行制御は変更していない。

停止試験後、確認画像のCRC・左右マーカー・ゼロ点とWeb HTML 113624 bytesの完結を確認した。別に行ったUSB診断では足タスクCore0/stack余裕2996 bytes、内部RAM最小9292 bytes。USB診断中にはHALの不完全画像破棄22件とEV-EOF-OVF 1件が出たため、内部破棄を解消したとはしない。これは上記の遅延測定とは別の約7秒間の観測である。USB診断はOFFへ戻し、ここまでモータ/測定開始指令0。歩行中の追従性と実際の前進は、バッテリー給電の動画/RWLOGで確認する。

起動直後の `READY_TO_MEASURE`／`ready=true` は、足角度のゼロ点確定を意味しない。今回も同じ画面状態で `zero_ready=false`・`foot_control_reason=zero_not_ready` の期間があった。上記Core1試験はゼロ点確定・両足有効を確認してから行った。歩行開始前も機体の状態表示と足角度の準備状態を分けて確認する。

ユーザーの準備完了後、USBポート未接続・バッテリー7.21 V・ゼロ点確定・左右有効・開始条件readyを読み取り確認した（boot885874075）。ユーザーが実験を自分で行うと明示したため、こちらから開始指令は送らず、ライブ照会も終了した。歩行結果は動画/RWLOGの受領後に評価する。

## 検証と復帰

### 11月17日のログ取得不通のコード調査

動画 `WIN_20261117_11_33_49_Pro.mp4` と「Failed to fetch」の申告後、HTTP状態/manifestとpingが不通だった。USB診断ではFINISHED（detail4）、制御/IMU/HTTPのheartbeat更新、export待機、同じUSB起動カウンタ1を確認。export待機は成功とエラーを区別できない。TP-Link再接続・物理差直し、内蔵Intelでの接続も試したが回収できず、アダプター単独故障とは断定しない。ユーザーは今回のログ消失を許可し、自分で電源再投入・再測定すると明示した。こちらは再起動・書込み・測定開始を行わず、その後の機体照会を終了した。

- **再現した実装上の弱点:** `compact_json_table.h` の `range()` は `String` への追加失敗を確認しない。Arduino Stringと同じ「確保失敗時は元の内容を維持する」モデルで値の追加だけを失敗させると、入力 `{"a":123}` に対して `{"fields":["a"],"rows":[[]]}` を出力し、append/finishともtrueになった。通常メモリ条件の同値試験では出ない欠落であり、修正対象。ただし今回のHTTP接続不通を再現した試験ではない。
- **原因候補:** 内部RAM最小空き4452 bytes。状態JSONは `String json; json.reserve(6100)` の戻り値を未確認で、ログ作成にも一時的なStringがある。PSRAM専用なのは大きな出力バッファで、すべての中間文字列ではない。ただし通常Stringの割当先はサイズ/設定次第であり、状態JSON全体が必ず内部RAMを消費すると断定しない。今回、確保失敗そのものの記録はない。
- **停止処理の確認対象:** `stopContinuous()`→`flushQueuedFrames()`→`cam_take(0)` は空キューでHALの `ll_cam_dma_reset()` を実行する。受信停止後の単なるキュー清掃にもDMAの副作用がある。Wi-Fiとの因果関係は未確認で、ドライバコメントのESP-IDF 5.2の記述だけを今回の環境に当てはめない。
- **原因と断定できないもの:** HTTP再開は `begin()` の結果を検査し失敗時に1秒おきに再試行する。SDKのWebServer::begin自身がcloseを行うため、WiFiServerだけを見たsocket漏れの推測は採用しない。AP/DHCPを測定時に停止するコードはない。ログ作成は協調yieldと容量検査があり、今回もタスクは待機へ戻っている。

再検証はブラウザ再試行・HTTP休止/復帰・送信時間上限のテストPASS。Core0へ戻した際に全容量テストの期待値だけがCore1のまま残っていたため、テストを0/1へ訂正した。実serializerのv25/v25native/v26全容量試験PASS、v26は1001422 bytesで1 MiB以内、足1280/エネルギー192/支持96件を保持する。これは実機のヒープ不足・無線ドライバ動作の証明ではない。

ローカル証拠は `analysis/2026-11-17-log-recovery/` のUSB診断2件、`metadata_audit.json`、`check_compact_alloc.py`/`compact_alloc_result.txt`、動画抽出画像。HTTP回収補助も同フォルダに残したがmanifest取得前に通信が失敗しており、ログ回収成功とは扱わない。実機ファームウェアの変更・修正書込みは未実施。次の修正では文字列確保失敗の検出とメモリ負荷低減、停止時の副作用のないキュー清掃、USBからのexport結果/通信状態の診断を優先する。

プロファイルのバス失敗・遅延読戻し、画像境界と所有権、従来座標との認識一致、プレビューと観測継続、全容量メタデータ、インストーラ識別をホスト試験で検証する。歩行成否・足接地・角度の動的な精度は停止試験から結論しない。

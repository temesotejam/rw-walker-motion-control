# v16-webfix2：診断履歴をPSRAMへ移す

2026-11-14、v16-webfix1でも操作画面の読み込みが終わらないという録画 `レコーディング 2026-11-14 123809.mp4` を確認した。約131秒の録画は初期文言の操作画面で始まり、60秒・130秒ではChromeの `ERR_CONNECTION_TIMED_OUT` が見える。前回の「HTMLを一回全長取得できた」という結果だけでは、継続使用の復旧確認になっていなかった。

その後のUSB診断では、同じ起動のまま `energy-pulse-lifecycle-v16-webfix1` がREADYで動作し、制御・カメラ・HTTP heartbeatは継続、AP接続1台・Wi-Fiイベント数4も変わらなかった。それでもPCのHTTP/ARPは到達不能になった。内部RAMは空き8992バイト、最小2004バイト、最大連続3060バイト、PSRAMは約1.70MB空いていた。再起動やアプリのHTTPループ停止では説明できず、通信に必要な内部RAMの余裕不足を有力な要因として対策する。単独原因と確定するには更新後の実機比較が必要である。

`ExperimentRunner` の192件分の `WalkingEnergyAudit` 配列は39936バイトを内部RAMに静的確保していた。専用ビルド `WALKING_AUDIT_PSRAM=1` では、これを起動時の `ps_malloc` で確保する。動作中の記録保存・終了更新にメモリ再確保はない。実入力の完了量・残留電流・pendingを更新する独立したactiveコピーは内部RAMに置いたままにする。

PSRAM確保に失敗した場合は履歴の保存件数を0に保ち、完了処理は独立activeコピーで継続する。metadataの `archive_storage`、`archive_available`、`archive_bytes` で欠損を識別する。保存容量192件や完了Q/Wの定義、歩行のエネルギー選択、MEKF、入力電流・幅の制約は変えない。記録用配列の配置を変える修正であり、歩行改善や実機の制御期限維持を検証済みとするものではない。

検証は `python tools/test_walking_audit_psram.py`。実v16の採用→保存→開始→停止→完了経路をPSRAM型でコンパイルし、確保成功・確保失敗・192件満杯・二重完了・pending/残留の整合、動作中に再確保しないことを確認する。実metadata serializerでも保存成功と確保失敗/空を検証する。従来v16の連結テストとmetadata/CSV回帰もPASS。

専用環境は `atoms3cam-energy-pulse-lifecycle-webfix2`、識別は `energy-pulse-lifecycle-v16-webfix2`。PlatformIO build SUCCESSで静的RAMは166780→126844バイト（39936バイト減）、Flashは1872921/3342336バイト。firmwareは1873280バイト、SHA256 `9e6d35d4ea9f7170f75b978b0bbbcc44427afc731952e844c1ee121a0ba485c9`。

`python tools/prepare_energy_pulse_lifecycle_webfix_flasher.py --psram` で `http://127.0.0.1:8767/energy-pulse-lifecycle-webfix2/` を準備する。page/manifest/4partsはHTTP200・ローカル全バイト一致を確認した。元v16/webfix1の配信物は保持する。実機では書込み後の識別・空き内部RAM・繰返しHTML/状態取得・接続維持を別途確認する。

## 実機の書込みと継続通信確認

同日、ユーザーがこちらでの書込みと通信確認を承認した。COM24（ESP32-S3 rev0.2、MAC末尾6a:d4）のREADYをUSBで確認してから、既存の `ENTER DOWNLOAD` を使用した。ビルドで使った `.platformio/packages/tool-esptoolpy@1.40501.0/esptool.py`（4.5.1）で `--no-stub write_flash -z`、DIO/80MHz/8MB、app0の0x10000だけを書いた。NVS・パーティション・ブートローダーは書き換えていない。1873280バイトの書込みとハッシュ検証が成功した。

書込み後、ソフトdownload用のRTC `FORCE_DOWNLOAD_BOOT` が残っていた。SDKの `RTC_CNTL_OPTION1_REG=0x6000812c`、bit0を確認し、ROMの `read_mem` で値1を確認した後、`write_mem 0x6000812c 0x0 0x1` でその一時ビットだけを消して再起動した。flash/NVS/eFuseの消去ではない。この経路で再び書き込む場合も、ROMに残っていないかを起動識別で確認する必要がある。最初のツール選択は別版4.9系の依存不足で接続前に失敗しており、実際の書込みは上記4.5.1だけで行った。

USB/HTTPの新識別を確認し、起動直後の内部RAM空き61728バイト・最小水位61340バイトを観測した。書込み用リセット後の理由はTASK_WDTと記録されたが、下記試験中に起動IDの変化はなかった。

181.5秒、ブラウザに近いHTTPヘッダーで229要求（HTML36回・状態193回）を実行し、全て成功した。HTMLは毎回95778バイト、SHA256 `bdf5416b9df799dd05c413cbcdade8a8a0ebf362fe49f8b70e9a756ac496ae01` と一致した。最後の3接続同時取得も成功、最大応答時間は1.093秒、HTTPのboot_idは4216065150で一定、状態はREADY・制御状態fresh・samples0を維持した。

USB診断180サンプルでは、観測した内部RAM空きの最小42824バイト、起動以来の最小水位38632バイト、最大連続領域の最小30708バイト。試験終了時は空き57492バイトだった。診断は試験後OFFへ戻した。ユーザーもCtrl+F5後に「状態・数値が表示された」と確認した。今回の範囲では通信と表示が復帰したが、歩行や長時間の制御期限を検証した試験ではない。

ローカル検証記録は `analysis/2026-11-14-web/flash_webfix2/summary_180s.json`、`http_180s.jsonl`、`usb_180s.txt`、`status_after.json`、書込みログ一式。生ログはGitHubへ送っていない。

## 詳細な原因分析（2026-11-14）

最も有力な主因は、エネルギー制御の検証用に追加した履歴配列を、通信とタスクのための余裕が必要な内部RAMへ固定確保したこと。設計上のメモリ配置の不備は確認できた。低メモリと通信停止の対応、PSRAM移設後のメモリ増加・継続通信成功も整合する。ただし失敗した個々のメモリ確保やTCP/Wi-Fi内部エラーは当時記録していないため、全ての通信停止を一つの確保失敗に結び付けた証明ではない。

### 配列はv14から導入され、v16でさらに大きくなった

過去の `experiment_runner.h` から実際の `WalkingEnergyAudit` 定義を取り出し、共通の純粋モデルヘッダーとコンパイルしてサイズを再計算した。3版の `walking_energy_policy.h` は同じGit blob `11be1c5a8e28e454530b493f100ed669f96aad50` であり、型の比較に同じ定義を使用できる。

| 版・コミット | 1件 | 192件の記録配列 |
| --- | ---: | ---: |
| v14 / 6fc5ddb | 132 B | 25344 B |
| v15 / 2d6a88f | 140 B | 26880 B |
| v16 / 3492e04 | 208 B | 39936 B |

v16では開始時電流、時定数、角速度、実終了時刻、終了理由、完了Q/Wなどの監査項目を追加し、v15から配列だけで13056 B増えた。各値は研究上の検証に有用だが、保存先の見直しを伴わなかった。グローバルな `runner` のメンバー配列なので、ログ件数が0でも領域全体を内部RAMに占有し、PSRAMの通常malloc設定では自動的に移動しない。記録件数192という上限があっても、通信に残る内部RAMが十分かという検証にはならなかった。

修正前後の対象ELFでは `runner` が63488→23552 B、ビルドの静的RAMは166780→126844 B。配列39936 BをPSRAMへ移した効果を確認できた。これらはバイナリの静的配置であり、実行中の空き量とは別の指標である。

### PSRAMの空きでは内部RAM不足を埋められない場合がある

ESP-IDFは能力の異なる複数のヒープを使い、タスクのスタックや一部のバッファには内部RAMが必要となる。Wi-Fi/lwIPも通信時にメモリを使う。今回のSDKは `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=1` なので、通信メモリの全てが内部RAM専用という説明も正確ではない。小さな通常確保は4096 B未満で内部優先、内部専用の予約量は0に設定されている。PSRAMの約1.70MBの空きが、そのまま内部RAMで必要な確保の余裕を意味するわけではない。

公式根拠: [ESP-IDF v4.4.7 外部RAM](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-guides/external-ram.html)、[ヒープと静的/動的メモリ](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-reference/system/mem_alloc.html)、[Wi-Fiバッファ使用](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-guides/wifi.html#wi-fi-buffer-usage)。

| 指標 | 不調時webfix1 | 修正後webfix2 |
| --- | ---: | ---: |
| USBで観測した内部空き | 8992 Bのサンプルあり | 試験180サンプル中の最小42824 B |
| 内部ヒープ最小水位 | 2004 B | 38632 B |
| 最大連続空きブロック | 3060 Bのサンプルあり | 試験中の最小30708 B |

最小水位は `heap_caps_get_minimum_free_size(MALLOC_CAP_INTERNAL)` の値で、1秒周期の空きサンプルの最小とは異なる。複数ヒープの低水位の合計という性質もあるため、全領域が同時にその値だったとまでは言わない。最大連続領域は一回の確保可能量を判断する指標になるが、用途ごとの能力条件も必要である。今回、メモリリーク、メモリ破壊、断片化の進行をトレースしたわけではなく、空きの減少だけでそれらを確定しない。

### 画面が初期文言のままになる経路と送信の打切り条件

操作画面は95778 Bあり、JavaScriptは受信本文の19638 Bから始まる。初回の失敗では16640 Bで切れたため、静的HTMLは表示されても末尾のscriptを実行できず、状態取得・ボタン有効化が始まらない状態と整合する。以前の19737 Bという値は、CRLFを含むローカルheaderの位置だった。C++で改行が正規化された実際の送信本文の位置は19638 Bであり、どちらを使っても16640 Bでは届かないという結論は同じ。

送信コードには、進捗があっても全体1200msで停止する弱点があった。webfix1で無進捗3000ms/全体15000msへ分け、ホストで低速送信を検証した。ただし初回の実機失敗の送信経過時間・errno・終了理由を記録していないため、「その16640 Bの失敗が必ず1200ms到達によるもの」とは断定できない。タイムアウトを延ばしても、内部RAMが不足した通信系を修復することにはならなかった。後の録画ではHTTP/ARPが届かない段階にまで進んだ。

### 一時的な接続不整合と書込み後の起動モードは別の問題

PCのWi-Fiが接続済み表示でも、機体USBは接続端末0台を報告した時期がある。その時は再接続で復帰した。一方、後の不調時は機体も接続1台を認識し、起動ID・イベント数・HTTP heartbeatが進んだまま通信が不通になった。この2つを同じ原因として扱わない。初期の電源OFFによる到達不能も、その時点だけの説明である。

今回の更新作業では、書込み成功後にRTCの一時downloadフラグが残り、アプリに戻らない問題も実際に確認した。これは書込み後の起動復帰の問題で、既に起動済みのwebfix1が後から通信不通になった現象の説明にはならない。Hash検証の成功と、アプリ起動・AP・Web動作の成功は別々に確かめる必要がある。

### カメラ用リポジトリとの関係

当時の実配信sourceは `1d17dec32772f593c2be1cf5b4704886b23458d3`。bootloader/partition/boot_app0のハッシュは歩行器版と一致した。`camera_coexistence.cpp/.h`、保存基準と重心ずれのRecord定義・読書き処理もGit blobが一致している。これだけで全ての保存データの内容を検証したことにはならないが、設定領域の破壊を示す証拠は得られていない。アプリ切替による再起動が接続の再確立を必要にした可能性は残るが、今回の継続通信障害の主因としてカメラrepoを断定する根拠はない。

### 実装・検証の反省と証拠の限界

- 診断履歴を増やす際、既存のPSRAMログと同じ配置方針を徹底せず、内部RAMの実行時予算を検証していなかった。
- ビルド成功、入力経路のホストテスト成功、RAM静的使用率50.9%という情報では、カメラ/RTOS/Wi-Fi同時稼働後の動的余裕を保証できなかった。
- ホストの送信ダブルは部分送信やENOMEMを模擬するが、実ドライバと内部ヒープの競合を再現するものではない。
- 全HTML一回の取得、PCの接続済み表示を復旧判断に使い、ユーザー画面と継続負荷の検証が遅れた。
- 書込み時は解決済みのesptoolバージョンの確認を怠り、別版の依存エラーで2回止まった。どちらも接続前で、元の通信不具合とは別件。

webfix2では同じHTMLの全長/ハッシュ、状態のfreshと起動ID、複数接続、USBのメモリ、ユーザー表示を合わせて確認した。しかしメモリ移設と再起動/再接続が同時に入っており、完全に条件を統制したA/B試験ではない。失敗した確保の要求サイズ/能力やWi-Fi内部エラーも未採取である。したがって「内部RAMを圧迫した保存設計は確認済み」「それが継続通信停止の最も有力な主因」「待機中の181.5秒では復帰を確認」が妥当な結論である。長時間・歩行中の安定性まで保証した結果ではない。

今後は診断項目追加時に `sizeof(記録)×容量` とメモリ配置を確認し、待機/カメラ/通信が重なる負荷で空き・最小水位・最大連続領域を測る。必要な制御状態は内部に保ち、履歴アーカイブは起動時PSRAM確保と欠損表示で扱う。再発時に備える送信終了理由/経過時間/送信済み量/errno、確保失敗時の要求サイズ・能力の軽量記録は追加候補であり、この分析では未実装。安全なメモリ閾値を今回の一試験だけから決めない。

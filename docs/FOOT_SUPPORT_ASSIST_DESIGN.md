# 足姿勢に応じた早期入力の設計レビュー

2026-11-11。v10の2試行、既存runner、足観測とCAD診断を調査した。これは次の実行版へ向けた設計レビューであり、必要トルクや実機での改善効果を同定した文書ではない。

## 推奨する最小の実行変更

既存の早期入力の承認・出力経路を使い、通常相当の幅の入力を、遅延補償した足の前振れ量と運動状態に応じた早い時刻へ移す。また、通常の提案がcoastのときは、足が前に出ており、機体の向心速度の持続的低下、または左右差を伴う足の前振れが戻る形状条件がある場合に限り、15 ms入力を試す。機体ゼロを待つ前に引っかかりへ接近する場面へ入力位置を移す仮説である。正常ZEROと足に応じた早期入力のどちらかを一つの半周期の入力として選び、通常ZEROへさらに別パルスを重ねない。

足側と機体ロール符号の物理対応は未確定。両足とも前に振ると角度が増えることはユーザー確認済みなので、まず `max(0, left, right)` と左右差の大きさを側に依存しない形状変化の代理量とする。モータ方向は従来どおり機体の向心方向から決定する。左右の足ラベルをモータ方向へ直接結び付けない。

足が前に出ていれば戻り中でも足裏形状は変化する。`Returning` を一律に対象外にしない。頂点付近で速度推定の確信が下がる場合は、外挿を控えて観測値保持または従来の角度条件へ戻す。足の角度だけから接地、支持脚、足裏反力を断定しない。

可変閾値、許可する角速度、見積もったZEROまでの時間の範囲は試験パラメータ。CADの未校正な高さ一致角から自動決定した値とは扱わない。取得遅れ・フレーム間隔・IMUで観測した運動により、その時点の推定を使う。

portable selectorは `src/foot_support_assist.h` に実装した。フレーム年齢160 ms以内、推定不確実性各0.75度以内、前振れ代理量1度以上、機体の向心距離0.8度以上かつ可変閾値以下、向心速度6〜45度/秒を条件とする。閾値は `1 + 1.2 * forward + 0.3 * asymmetry` を1.5〜5度へ制限する。前振れ量と左右差からは推定不確実性を差し引く。これらの不確実性は内部の推定であり、真値を必ず含むと保証する誤差境界ではない。

最初の案は閾値上限3度、速度上限35度/秒、通常driveの移動だけだった。しかし今回の2runの既存tilt状態を再現した因果再生では候補が0となった。大きい前振れが強い負ピークに対応し、通常提案がovershoot coastになりやすいためである。範囲を拡張しcoastでの減速時入力を追加した変更は、このログから得た試験仮説であって、独立した歩行改善の検証ではない。

## 実装の接続点

- v10は `atoms3cam-balance-trim` を継承するため `FOOT_EARLY_TRIAL=1` と `ANGLE_EARLY_TRIAL=1`。`updateEnergyControlAutonomousMotion()` は `tryAngleEarlyCandidate()` を選び、既存 `early_motion_gate_` のカメラ候補経路を使わない。新しい足依存条件を加えるなら、この角度候補経路の専用ビルド分岐が最小。
- `tryAngleEarlyCandidate()` は現在±1.5度の入口を持つ。後段だけ可変閾値を広げても入口で切られるので、専用版の入口と本判定を揃える。従来版の範囲は変更しない。
- `decideAngleEarlyCandidate()` の `angle_late_blocked_peak_ms_` と20〜30 msの見積もり時間も固定条件に結び付いている。新しい閾値や時間窓に合わせる際は、旧条件が後から候補を封じないよう専用版の意味を整理する。
- `acceptOptionalEarlyMotion()` を共通の承認入口として使う。ここにあるrun状態、向心方向、ピークID、前回入力からの最小間隔、WAIT_ZERO_CROSS、緊急停止、出力中の除外を維持する。
- `tryTiltPriorityOptionalEarly()`、`tryTiltPriorityImpl()`、`dispatchTiltPriority()`、`beginEnergyControlAutonomousPulse()` を通す。別の直接モータ書き込み経路を追加しない。既存のバッテリ、IMU、車輪速度、電流、パルス幅、送信不確実性の処理をそのまま通す。

## 15 ms置換の問題と通常幅の保持

現在の早期入力は、通常ZERO入力へ15 msを加算するものではない。早期入力が実行されるとその半周期を消費し、後の通常ZEROで約50 msのパルスをもう一度出すことはない。

従って、単に弱い側の入力を早めるために通常相当の幅を15 msへ縮めると、投入量を減らすことになり得る。`tilt_priority::Controller::deferEarlyWhenWeak()` は、直近の対応ピークが弱く通常候補の幅の方が大きいとき、早期15 msを拒否して通常ZEROを残す。これは従来の15 ms入力には維持する。

新しい足由来の入力では、通常の提案幅を基準にした入力を、足に応じた早い時刻へ移す。selectorは幅を縮めず、そのまま採用できる場合だけ候補にする。通常幅が60 msを超える場合は60 msへ丸めず不採用とする。見積もったZEROまでの時間が幅+20 ms以上、かつ250 ms以下の場合だけ許可する。後段の車輪・タイミング等のガードで幅が減る場合は `widthPreserved()` が拒否し、通常ZEROの機会を残す。

通常proposalを取得するときは通常と同じhardware capを使う。その後proposal幅をhardware capに入れ直して再提案すると、速度に応じたtaperが二重に適用され、弱い幅へ変わり得る。新しい入力は通常proposalを一度取得し、その幅がselectorの幅と一致することを確認して後段ガードへ渡す。

この方式は、早期判断時点の通常幅を維持するもので、まだ到達していない将来のZERO時点の幅を同定したものではない。未来の機体角速度や車輪速度は入力によって変わる。60 ms上限、20 ms余裕、250 msの時間窓も安全性や必要仕事を保証する実測値ではない。実行版の作成を、パワー不足の解決や連続歩行改善の実証とは扱わない。

## 通常coastで限定した根拠がある場合の15 ms入力

`normal_coast_selected=true` だけでは入力を許可しない。同じrun・ピークの向心運動について、別の因果的な速度検出器が `inward_decelerating=true` を示すか、次節の `anticipated_shape_need=true` がある場合だけ、15 msを候補にする。既存の足品質、前振れ代理量、機体位置・速度、画像年齢、時間余裕、車輪・ハードウェア保護も全て通す。幅15 msが後段ガードで短くなると不採用とする。

通常driveとcoastの両フラグが同時にtrue、またはcoastなのに通常提案幅が0でない場合は不整合として拒否する。`Decision.coast_assist` で通常幅移動とこの入力を区別する。根拠がない場合の理由は数値16の `CoastNeedsEvidence`。以前の `CoastNeedsDeceleration` は同じ値の別名としてソース互換性を保持する。

速度検出器は、同じrun・ピークの短い最近の窓からの4度/秒以上の低下が10 ms以上持続することを確かめる。外向き運動、中心通過、ピーク更新、IMU欠測・古いサンプルでは状態を消す。古い速度最大値を長く保持すると、関係のない後の運動まで減速扱いになるため、参照速度の寿命を制限する。単発gyroスパイク後の復帰を証拠としないよう複数の新鮮サンプルが必要である。

この分岐は、以前の大ピークに対するovershoot coastの判断を限定条件で上書きする実験である。以前と同じ15 ms上限でも、従来と同じエネルギー抑制を保証するものではない。前振れによる抵抗を実測したとは扱わず、入力後のピークと足運び、前進の継続を独立に確認する。

### 足の左右差と戻りによる先行条件（2026-11-12追記）

実際の持続減速だけを待つ案でも、今回の因果再生で有効候補が現れなかった。そこで、減速が観測される前から限定的に試す条件を後付けの仮説として加えた。ユーザーが説明する「前に振れた足が戻る間、足裏の左右円弧形状が変わる」という問題に合わせ、機体ピークが大きい・小さいことを支持切り替え成功の証拠には使わない。runnerが次の条件を全て確認した場合だけ `anticipated_shape_need=true` とする。

- 不確実性を差し引いた前振れ代理量が1度以上である。
- 左右差の大きさから左右それぞれの推定不確実性を引いた量が1度以上である。
- 上の前振れ代理量を作る主要な足の予測状態がReturningである。単にどちらか一方の足がReturningというだけでは不足。
- 直前の入射側機体ピークが8.5度以下である。これは過大な揺動中の追加入力を避ける上限であって、歩行や支持切り替えの成功判定ではない。

portable selectorはこのboolを検査するだけで、足のphaseや直前ピークを独自に推定しない。runner側が条件の所有者であり、run変更と履歴不整合時に無効化する。監査では `inward_decelerating` と `anticipated_shape_need` を分けて記録する。

この条件は、通常coastとなる場面でも、左右差のある前振れが戻る間に支持を移すための前置き入力15 msを試す根拠である。前振れ量と左右差はカメラ相対角に基づく形状変化の代理量であり、実際の減速、接地、支持反力や形状抵抗の実測を意味しない。次側の小さい機体ピークの反復は、この条件には採用しない。同じデータから条件を追加したため独立した性能検証とは扱わず、実機の介入後の応答と連続歩行は未検証とする。

## 遅延と候補の寿命

足角度を制御が最初に見るまで、ドライバ時刻から約77 msかかる。カメラ更新は約100 ms。カメラ処理時点で予測を一度計算するだけでは、その後の制御で同じ結果を再利用する経過時間が残る。実行判断時刻における画像年齢を必ず再計算する。

候補にはrun ID、フレームsequence、フレーム時刻、推定の対象時刻、足の左右有効性と校正範囲、推定状態と不確実性を持たせる。実行直前に、runが一致し、時刻が未来でなく、画像が十分新しく、推定範囲が足を前へ振っていることを支持する場合だけ足による変更を使う。無効・欠測・古い画像・原点準備前は、従来の制御へ戻す。これにより不確かな観測で新しい入力を許可しない一方、カメラ無効だけで従来制御を止めない。

フレーム時刻と実露光時刻の厳密な対応は未校正。固定のカメラ遅延、通信遅延、モータ応答時間を確定済みの実測値として扱わない。

## 重複・失敗時の不変条件

1. 正常ZERO、通常の救済、早期入力が同時に成立すれば、既存順序どおり正常側の検出を優先する。同一IMUサンプルで足による早期候補と従来の早期候補を別々に試行しない。
2. 早期候補を承認したピークのIDは `optional_early_attempted_peak_ms_` で記録し、そのピークの間に繰り返し試さない。フレーム更新や推定状態の切り替えでこのIDを消さない。
3. 実行された早期入力はその半周期を消費する。通常ZEROでの再入力を許可しない。
4. `deferEarlyWhenWeak()` やハードウェア条件で送信しなかった場合は、既存の状態復元により通常ZEROの機会を残す。同じカメラ候補を繰り返し再試行しない。
5. モータへの書き込み失敗は、モータが受け取っていない証拠ではない。`optional_early_write_uncertain_` による停止を維持し、状態を戻して通常ZEROを重ねない。
6. run開始・中断・終了・epoch変更で新しい足推定の状態と候補を初期化する。古いrunのフレームを新しいrunへ持ち込まない。

## 記録と検証

新しい版では、足由来の候補と従来角度由来の候補を識別可能にする。少なくとも候補の時刻、採用した左右足角、画像年齢、前振れ量、足の状態、機体角・角速度、可変閾値、見積もり時間、試行したピークID、実際の幅と出力結果が必要。候補が成立しただけでは実際に実行されたと言わない。

ホストで確認する不変条件は、run変更・古い観測・将来時刻・両足の品質・閾値境界・向心/外向き・正常ZERO優先・一ピーク一回・送信なしの復元・曖昧な書き込み停止・通常幅の保持・新しい通常幅の60 ms上限・coastでの15 ms上限・coast単独での拒否・従来版の不変性。portable selectorの `tools/test_foot_support_assist.py` は時刻・方向・閾値・幅と不確実性境界、および減速証拠と先行条件の独立した許可を確認する。runner統合、持続減速の検出、足のphase・形状代理量と入射側ピーク上限の確認、およびモータ送信の不変条件は、別途統合テストで確認する必要がある。過去ログで候補を再生した場合も、実際の入力後の運動を再現したものではない。

実機評価は、毎回の足の前振れと支持の移り変わり、連続した前進、余分な揺動が減るかを映像とログで比較する。揺動が30秒続くことやピーク数だけを歩行成功の基準にしない。

# v16 パルス開始・終了時刻と完了監査の独立レビュー

2026-11-13。v15の実機記録を受け、予定入力幅とソフトウェア上の指令生存時間を区別する。時計修正と完了監査を確認する文書であり、電流積分・機械仕事・連続歩行を実測で検証したものではない。

## v15で見落としていた経路

v15は、電流指令要求が受理された後へ入力開始時計を置き直した。`setCurrentMa` の成功はキュー投入の受理であり、ドライバ書込みや実電流開始の完了ではない。一方、外側ループはその処理より前に取得した `now_ms` を、同じループのパルス終了判定へ渡していた。古い `now_ms - 新しい開始時刻` を符号なし整数で計算すると巨大な経過時間に見え、受け付けたばかりの長い入力が直ちに終了し得る。

以前のレビューは開始関数の時刻再設定を確認したが、開始と終了判定を同じ古い外側時刻で連続実行するテストが無く、この問題を見落とした。予定80msや予定Q/Wの記録から、実際にその指令期間を維持したと判断できない。

v16は終了判定の入口で時計を読み直す。実機の実入力期間を監査せずに、v15の予定仕事量と次ピークとの関係から仕事モデルを再同定しない。参照エネルギーやゲインの変更は時計修正と分け、v14の実際の動きも比較対象として保存する。

## 時間とエネルギーの記録契約

検出/判断時刻、キュー投入受理後の開始時刻、予定幅、停止要求時刻、ソフトウェア経過幅、終了理由を別に記録する。この経過時間は `queue_accept → stop_request` で、実電流のオン/オフ時間ではない。実経過時間を予定80msやQ表100msへ切り詰めない。長い遅延や途中停止があれば、その差をそのまま残す。

現在の経過幅はmillisの整数ms分解能である。0msの記録も、1ms未満の指令生存時間や実電流を否定する測定ではない。0msに対するモデルQ/W=0は、この分解能とモデルへ入力した時間に対する値である。

完了時は、開始時の符号付きI0、予測飽和電流Ig、立ち上がり時定数tau、入力方向、判断時角速度、available/requestを使い、実経過時間Tから解析的に再計算する。

```
Q_mAs = Ig*T + (I0-Ig)*tau*(1-exp(-T/tau))
I_end = Ig + (I0-Ig)*exp(-T/tau)
W_pred = inherited_work_model(rate, Q)
arrival_pred = available + W_pred
unmet_pred = max(0, request - W_pred)
```

これは実電流の積分や機械仕事の測定ではない。指令トランザクション中の電流開始/終了時刻、電流モデル誤差、ホイール・足の交換は未同定のまま残る。負の正味Qはその符号を保存し、`abs(Q)` や二次項で正の励振仕事へ読み替えない。その場合、正の励振用仕事式のW/到達/未達は無効とする。

予定時間と実時間が異なる場合、次の入力の初期電流が誤らないように残留電流値とその終了時刻を実経過時間へ合わせる。対応するpending半周期だけのQ/モデル到達予測を更新し、別の時刻/側のpendingを上書きしない。終了監査は同じパルスにつき一度だけ行い、未送信の候補を完了入力として扱わない。

## 独立テストの範囲

`tools/test_energy_pulse_lifecycle_v16.py` は実際の開始関数と終了判定関数を連続して実行し、v15の古い時刻による即時終了を再現する。同じ条件のv16、v14参照、要求受理まで0/1/7ms、判断前の経過、millis折返し、受理失敗を比較する。実ESPのスケジューラや物理的な電流オン/オフを検証するテストではない。

完了更新については `tools/test_energy_pulse_completion_runner_v16.py` が実ファームウェアの監査構造体と `finishWalkingEnergyPulse` 本体を取り込み、最小限のhost状態で実行する。ゼロ経過、通常完了、早期中断、100ms超の遅延、時計折返し、二重終了、無関係なpending、負の正味Qと入力無効を確認した。期待値はproduction helperの再呼出しではなく、一次電流モデルを独立に解析積分して比較した。

解析ヘルパー `energy_pulse_completion.h` はQ表の上限を積分上限にせず、実経過時間を全て積分する。モデルの幅/角速度/Q支持範囲を別フラグにし、外挿や無効仕事を記録する。

## 最終確認結果

独立実行で次が成功した。

- `python tools/test_energy_pulse_lifecycle_v16.py`：v15で即時終了15条件を再現し、v16では同じ試験集合の72条件すべてで選択した全幅を保持。v14参照も72条件成功。
- `python tools/test_energy_pulse_completion.py`：解析Q/終了電流、0/17/80/123ms等、符号付きQ、100ms超の非切詰め、電流表と独立数値積分との照合。
- `python tools/test_energy_pulse_completion_runner_v16.py`：42組の経過時間・初期電流・入力側に加え、理由1〜4、実時間0・途中停止・通常完了・123/1000ms・時計折返し・記録上限到達・pending不一致・二重終了を確認。

終了更新は記録配列とは別のactiveコピーで保持され、192件の保存上限に達しても制御用の残留電流/対応pending更新を止めない。対応pendingにはtrigger時刻と次側の両方の一致を要求する。現在/予定の意思決定値は保存したまま、完了の予測値を別フィールドへ記録する。

実ソースの呼出しでは、通常の `stopActivePulse` は理由1、`stopMotor` は理由2、緊急停止要求は先に理由3、run終了は先に理由4で完了させる。pendingフラグとactive indexを最初に解除するため、続く共通stop経路でも二重計算しない。未送信候補や既完了記録は終了した実入力として更新しない。

今回の確認はキュー受理後のソフトウェア指令生存時間と、その時間を仮定したモデルQ/Wの整合性である。実電流がその全期間流れたこと、必要機械仕事が実際に入ったこと、修正後の連続歩行を確認したこととは区別する。次の実機記録では、完了経過時間と独立した電流観測・動画を照合する。

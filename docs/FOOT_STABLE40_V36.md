# 有効更新40 Hz以上の検証：v36/v37（2026-11-17）

ユーザーは平均値だけでなく、安定した40 Hz以上を要望。v35の26 ms設定は理論上限38.46 Hzで届かないため、独立したv36で23 ms（設定上限43.48 Hz）へ短縮する。HB96、画像全体の検証、左右全17候補、校正、エネルギー方式、モータ制限は維持する。

## 高速化に伴う整合性

- `FOOT_STABLE40_V36` / `atoms3cam-foot-stable40` / `walking-foot-stable40-v36` はv35の軽量Webを継承。
- 足ログ1760件、metadata hard1408 KiB/reserve1536 KiB。同期5 s＋歩行30 s＋同期5 sを23 ms周期で保存できることをstatic_assertする。実serializer→RWLOG→CSVでも1760件の末尾まで確認。
- 予測器の旧25 ms下限では23 ms画像がGapとなり、実observer統合テストでReadyにならなかった。v36のみ最小間隔15 msへ対応させ、約20 msのセンサー画像の時刻量子化・揺らぎに余裕を持たせた。3つの予測器で14/15/20/23/25/40 msを検証し、旧版の25 ms条件を保持。同一画像・時刻逆転・古い画像・80度/s超や8度超のジャンプ拒否は維持。動的角度真値による精度保証ではない。
- 試験の静止ウォームアップは最終120画像にし、20 ms周期でも静止時間を確保。製品のゼロ点待ち時間は変更していない。

v36では更新数は40 Hzを超えたが、ときどき約40 msの間隔が残った。既存のnative取得関数は、取得開始時に待機済みの完成画像を捨てて次の完成を待つ。23 ms周期が約20 msのセンサーより遅いため間引きが起きる可能性がある。HALは変更せず、v37 `FOOT_CADENCE20_V37` / `atoms3cam-foot-cadence20` / `walking-foot-cadence20-v37` でワーカー周期を20 ms、足ログ2048件へ変更して比較する。metadata予算/予約はv36と同じで、全2048件・エネルギー192・支持96件を含む実serializer出力1279564/1441792 bytes。PSRAM余裕モデル312915 bytes。

## 安定性の測定

本体の初回制御受取りヒストグラムを拡張し、両マーカー検出に成功した観測同士の間隔を0.5 ms刻み128ビン（末尾63.5 ms以上）で数える。検出失敗を飛ばした時間も次の有効更新までの空白に含む。50 ms超の回数を独立集計。最後の有効受取りとスナップショット時刻を公開し、末尾の停止も隠さない。

5秒ごとの全受取り/両足検出回数を16区間、80秒のリングで保存。測定境界をまたぐ不完全区間は除外し、完全な5秒区間の最低有効Hzを確認する。区間ごとの検出数が保存されていなければ0として扱う。計測中のHTTPを避け、開始・終了だけ読み取る。

「40 Hz以上」は有効受取りの平均と各完全5秒区間の40 Hz以上を確認する。これに加えてp95/p99更新間隔、50 ms超の空白、検出率を提示し、平均だけを根拠に一定25 ms間隔と呼ばない。USB静止・通信なしとWeb負荷ありを分ける。歩行中の制御deadlineや動的検出率は別途実験が必要。

## 検証と保全

実observer統合（旧26 ms/v36/v37）、3予測器の短周期と異常拒否、ヒストグラムの重複拒否・検出失敗を含む間隔・50 ms境界・5秒境界・80秒リング再利用・最大JSON、21インストーラ構成を検証。全足1760/エネルギー192/支持96行を保持したmetadataは1175307/1441792 bytes。PSRAM非driver余裕モデル416595 bytesは実ヒープ・断片化の保証ではない。

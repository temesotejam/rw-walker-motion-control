# 足観測 v24：受信中の画像特徴計算

2026-11-16。`atoms3cam-foot-overlap` / `walking-foot-overlap-v24`。
USB接続中のモータ禁止を維持して、停止状態で実装・書込み・比較した。
エネルギー制御はv19を継承する。この変更はイベントホライズンMPCの実装ではない。

## 変更の目的と確定条件

v23では画像全体の受信後に左右の認識を開始した。v24は画像の上側に写る右足の必要26行が到着した時点で、その画素を独立した8,320 byteのPSRAMへコピーし、残りの受信と画像特徴の計算を重ねる。計算時は取得待ち中に空いている既存の内部RAM行バッファを一時利用する。右足の全17高さの探索を維持する。下側の左足は従来の受信後処理を行う。センサーの露光・解像度・クロック・マーカーの判定閾値はv23と同じ。

先行処理は候補の抽出だけで、追跡履歴・再捕捉・ゼロ校正・制御への公開を進めない。完全な320×240の画像と有効なdriver時刻を確認し、先行候補の64bit時刻がその画像に一致した場合だけ、確定時点の追跡状態へ反映する。不完全画像は従来どおり破棄し、候補が無い・時刻が違う場合は通常の全探索へ戻る。先行処理はカメラHALの高優先度タスクではなく足観測タスクで行う。

バッファはatomic状態遷移で所有権を管理する。DMAが使う画像のポインタを足タスクに渡し続けず、コピー済みの行だけを読む。取得待ちは同じ期限で1 tickずつ待ち、短い待ちごとにDMAをリセットしない。全期限経過時だけSDK由来の復旧を行う。復旧後の追加待ちがあるため、APIのtimeoutは厳密な実時間上限ではない。

## 計測の意味

- 比較対象はdriverの画像記録時刻から制御側の初回受取まで。driver時刻を物理的な露光開始時刻として校正したわけではない。
- `recognition_us`は受信後に残った認識処理。`upper_prepare_us`は採用した先行計算の経過時間で、最終版ではmailboxから内部RAMへのコピーも含む。認識仕事全体が消えたわけではなく、受信との重なりで待ち時間を短くする。
- `capture_wait_us`には先行計算中の時間も含む。先行候補を捨てた画像にも仕事は発生しうるため、採用分の二つの時間の合計は全CPU負荷を表さない。
- `upper_attempts/hits/misses`とmailboxの`offered/busy/replaced`を診断へ追加。各画像の採用有無と先行計算時間をRWLOG/CSVに保存する。
- 停止中にHTTPで抽出した画像の分布と、全フレームのカウンタ差を区別する。歩行中の遅延・追従性は次の実測ログで確認する。

今回の中央値短縮は1.9115 ms、約4.00%。受信後の仕事を前へ移した効果であり、最大ボトルネックの画像受信約36 msは変わっていない。v24の先行計算中央値は2.321 ms、先行計算と受信後認識の画像ごとの合計中央値は5.010 ms。計算全体を半減したわけではない。追加コピーもあり、持続取得頻度は約1%低く、フレームレート改善も主張しない。

最終版はboot `4290887638`が一定、READY_TO_MEASURE、全返信でMEKF/制御fresh、motor0/running=false、command投入0。観測区間179.460秒の完全画像4736枚すべてで先行結果を採用、miss/busy/replaced増分0。認識/観測失敗の増分0。先行計算は4983回で、完成画像に採用されない候補もある。制御受取時刻の未記録6標本はHTTP snapshot時点でまだ記録がないもので、遅延0や欠落と数えない。

## 検証

- 分離した画像特徴処理と従来処理を17,682件比較。全8結果、放棄した候補、元画素の破壊、時間境界・wrap・別マーカーを検査。一致。
- 非v24の認識差分13,256件一致。実FootObserverの5構成で通常/先行採用/不一致/欠損/時刻異常/タイムアウトと画素寿命を検査。
- 実HALを使う完全・不完全画像、DMA所有権、mailboxの交差動作、期限直前の完成画像優先・wrap・復旧回数を検査。
- metadata revision24/25、foot1280件・energy192件・support96件の保持、非ゼロの新列の往復を確認。最大metadata 1,000,041 byteで1MiB以内。任意の予測明細は従来同様truncatedを明示。
- PSRAM mailboxから再利用する内部scratchへのコピーも、元画素/行索引の寿命終了、26必要行それぞれの欠落、無効view、容量不足を検査。失敗時は古いcacheを無効にし、候補を確定しない。
- 最終ビルドSUCCESS（58.066秒）。RAM 128,940 / 327,680 byte、flash 1,932,505 / 3,342,336 byte。実行時の内部RAM余裕は別途USB診断で確認する。
- taskラップのリンク確認、旧インストーラ保全、新インストーラHTTPバイト照合を実施。

## 初回試作で検出した問題

内部RAMにmailboxを置いた初回試作は、制御受取中央値45.936 ms（基準47.7605 ms）、3953フレームすべてで先行計算を採用した。しかしUSB診断で内部空き22,696 byte、起動以来の最小3,240 byteと余裕が少なかった。このため最終版ではmailboxをPSRAMへ移し、既存の内部行バッファを取得待ち中の計算に再利用した。足タスクのスタック容量12,288 byteは維持する。初回試作のhashは `8d569dfc0e63ad9b06d75db241d257af193511423b111a73361d3d4e47026b2e`。

初回180秒プローブにはHTTPタイムアウト6件があり、最初の有効返信は起動52.329秒だった。エラーの個別時刻を保存していないため起動直後だけの問題とは断定しない。観測できた149.548秒では同一boot、認識・制御fresh、モータ0を維持した。初回USB受動観測40秒では不完全画像57件、OVF0件。これらを最終版の結果と混ぜない。

最終版は起動確認後のUSB診断で内部空き32,344 byte、起動以来の最小12,776 byte、最大連続空き22,516 byte、足タスクのスタック余裕3,364 byteを確認した。180秒測定後のUSB診断では内部空き30,996/min12,036/largest21,492 byte、足stack余裕3,364 byte。HTTPのmemory値は診断時のキャッシュであり、連続測定値ではない。初回試作の内部mailbox案より余裕が増えた。PSRAMバッファのホスト概算は7,203,757 byte（明示バッファ控除後の概算残り992,851 byte）であり、実機ではPSRAM空き933,819 byte。断片化や実行中の全ピークをホスト概算だけで保証しない。

最終版USB受動観測40秒では不完全画像48件、OVF0件。v23の以前の40秒観測は不完全画像40件/OVF1件で、条件・時間が異なる短い標本でもあるため欠落低減を主張しない。観測タスクの失敗カウンタ0は、HAL内で不完全画像を捨てていないという意味ではない。

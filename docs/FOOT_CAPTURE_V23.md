# 足観測 v23：カメラ記録時刻から制御側受取までの短縮

2026-11-16。対象は `atoms3cam-foot-capture` / `walking-foot-capture-v23`。
USB接続中はモータを動かさないという指示を維持し、停止状態で書込み・比較した。
エネルギー制御はv19を継承し、イベントホライズンMPCは今回実装していない。

## 変更と目的

- カメラのクロックを20MHzからPLL160/7、名目22.857142MHzへ変更。SDK初期化は20MHzで行い、起動時に受信を止め、XCLKをゲートして既知の分周設定を確認してから変更する。変更後は受信を再開して最初の画像を確認する。
- HB128、SDKの露光/AEC設定、320×240、左右それぞれ17高さの探索、閾値・マーカー追跡条件を維持。細い1ラインへ削らず、これまでの探索範囲を保つ。
- 内部DMAの総容量を増やさず、転送チャンクを半分にして物理スロットを2→4、イベントキューを1→3とする。ノード/フレーム境界の整合を確認し、未知の構成なら初期化を失敗させる。キューだけ増やして未処理画素の上書きを許す変更ではない。
- 認識の最大値比較を整数でまとめ、重心計算の64bit積和を上限確認付き32bitへ置換。出力・追跡状態の差分照合13,256件一致。画像・判定の意味を変更せず計算量を減らす。
- 停止中もCore1で観測の初回受取時刻だけを記録する。歩行制御器へ観測を投入せず、測定・モータを開始しない。`status.json`の`foot.driver_to_control_ms`と`ready_to_control_ms`で全体を計測できる。

`atoms3cam-foot-speed-receipt`は従来v22-fix1に同じ停止中の時刻監査だけを追加した比較用環境。旧環境/旧インストーラは保持した。

## 比較結果（停止中、HTTP応答後1秒間隔）

各値はHTTPで抽出した異なる画像の中央値。全フレーム分布でも歩行中の分布でもない。

| 項目 | 従来v22-fix1＋受取計測 | v23最終版・3分確認 |
|---|---:|---:|
| 記録時刻→画像受取 | 41.200 ms | 36.080 ms |
| 認識処理 | 5.784 ms | 4.423 ms |
| 記録時刻→認識/予測完了 | 53.000 ms | 46.440 ms |
| **記録時刻→制御側初回受取** | **54.518 ms** | **47.701 ms** |
| 同上p95 | 58.709 ms | 53.138 ms |
| 同上最大（抽出画像） | 64.588 ms | 68.661 ms |
| 初回受取が確認済みの標本数 | 143 | 161 |
| カウンタからの持続取得頻度 | 22.586 Hz | 26.814 Hz |
| 抽出画像の左右両検出 | 149/149 | 167/167 |

全体の中央値で6.817ms、約12.5%短縮。p95も短縮したが、抽出した最大値は改善しておらず、最悪遅延の保証ではない。標本数が応答数より少ないのは、HTTPがCore1初回受取より先に新しい画像を取得した標本を除外するため。未受取を0msとして平均しない。p95はソートした値の`floor((n-1)*0.95)`位置。

候補3分では同一起動ID、全応答MEKF/制御fresh、motor指令0、run0、command投入0。168応答/HTTP失敗0。画像取得4,819件中、マーカー失敗カウンタは左右各1増えた（抽出標本間の失敗）。従来比較の180秒プローブは149応答/HTTP失敗4、最初と最後の正常応答の時間差159.613秒から更新頻度を計算した。通信差の原因をカメラ変更だけに帰属しない。

USB40秒の別観測では、従来は不完全画像18回/受信イベントoverflow25回、候補は不完全画像40回/overflow1回。**不完全画像は残る。** これらは重複し得るエラー分類で、合計を厳密な欠落フレーム数としない。不完全画像は従来どおり破棄し、76800byteが揃うまで認識へ渡さない。CPU/ネットワーク負荷・明るさの全条件を網羅した保証ではない。

旧歩行ログ41601702の50.357msと今回の47.701msを同条件A/Bとして比較してはいけない。停止中にはプレビュー生成があり、歩行中には足履歴予測等の負荷がある。次の歩行ログで同じ区間を再集計する。カメラdriverの記録時刻は物理的な露光時刻として校正していないため、実際の足の運動からの遅延をこの値だけで断定しない。予測補償で見かけ上数値を短くした変更ではない。

## 試行中に棄却・修正した点

1. 24MHzの分数分周候補は画像欠落/イベントoverflowがあり採用しない。分数分周そのものが原因と確定したわけではない。SDKへ単に24MHzを渡すと整数分周で26.67MHzとなる経路があるため、その指定もしない。
2. 最初のクロック切替版は`cam_stop`後に起動用の`cam_start`がなく、カメラの初期画像待ちで失敗した。再開を追加し、起動順序の検査と実機確認を行った。
3. 整数分周7だけでも欠落/overflowがあり、4スロットのDMA受信へ変更した。
4. 複数の初期HTTPプローブはPC側sandboxの`WinError10013`で失敗した。機体の通信故障とはせず、権限付きの読取で再測定した。
5. 書込み後のreset表示には`TASK_WDT`がある。USB再起動操作を含むため、この表示だけで測定中の自然再起動とは判断しない。安定観測中の起動IDの変化を別途確認する。
